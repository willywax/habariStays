Executive Summary

Habari Stays is a React (Create React App) single-page app backed by a FastAPI/PostgreSQL API on Google Cloud, currently live with real production infrastructure but very thin real content: 30 live hotel listings, 100% in "imported" (unverified, Google-Places-scraped) status, concentrated in just Musoma and Arusha — despite the homepage, footer, and sitemap advertising Dar es Salaam, Zanzibar, Dodoma, and Moshi, where zero hotels currently exist. No hotel has real coordinates, almost none have a real description, and pricing is a uniform placeholder (mostly a flat 50,000 TZS) rather than researched per-hotel pricing.

Code review surfaced several security issues that need immediate attention: public registration accepts a client-supplied role field with no server-side restriction, a payment-confirmation endpoint has no authentication at all, and several hotel/room-editing endpoints have a broken authorization check letting any logged-in traveler edit another hotel's rooms. The live site also has a severe performance problem — the API consistently takes 13–20 seconds to respond — and the admin dashboard's source file currently has an uncommitted syntax error that would break the build if deployed as-is.

On the positive side, the core architecture is sound, the cashier dashboard is genuinely well-built and mobile-responsive, and the owner revenue/booking analytics are more sophisticated than most early-stage hotel platforms.

SEO Audit

Verified live via curl + code citations

The homepage has genuinely good static SEO: real title, meta description, keywords, canonical link, full Open Graph + Twitter Card tags, and two JSON-LD blocks (Organization, WebSite) baked directly into public/index.html — actually crawlable without JS.

Critical — every other page's SEO tags are dead code

react-helmet-async is listed in package.json as a dependency but never imported anywhere. SearchPage (App.js:1055-1057) and HotelDetailPage (App.js:1235-1262) write <title>/<meta>/JSON-LD as JSX directly in the page body. With no head-portal library, these render as inert DOM nodes inside #root — they never reach the real <head>. Every hotel and search page shares the homepage's title/description/OG-image on Google and on social shares (WhatsApp, Facebook, X unfurls included), and the hand-written per-hotel LodgingBusiness structured data never actually ships.

High — sitemap advertises cities with zero inventory

sitemap.xml lists dedicated pages for Dar es Salaam, Arusha, Zanzibar, Moshi, Dodoma, Mwanza. Live inventory today covers only Musoma and Arusha. 4 of 6 sitemap city pages return zero results — a thin-content signal that reads to Google as broken or abandoned.

SEO gaps — summary

  1. No react-helmet-async usage despite being installed — per-page tags never reach <head>.
  2. Search and hotel-detail pages are invisible to non-JS-executing crawlers and link-preview bots.
  3. Structured data is written but never delivered.
  4. Sitemap lists 4 cities with zero live inventory.
  5. Two URL shapes for the same hotel page (/hotel/:id and /hotels/:city/:slug) with no canonicalization between them.
  6. No sitemap entries for individual hotel pages at all.

Guest Flow Analysis

Inferred from code — exact file:line cited, not click-tested live

Guests can browse fully anonymously. The homepage hero collects City / Check-in / Check-out / Guests; SearchPage filters actually wired to the API are city, min/max price, and sort — no amenities or room-type filter, no pagination (the entire result set loads in one request).

Bug — date picker is decorative

The homepage hero collects real check-in/check-out dates and puts them in the /search?... URL, but SearchPage only ever reads city back out (App.js:1015, 1038-1049). A guest who picks travel dates gets results with zero availability filtering — the dates are silently discarded.

Hotel detail page: photo gallery with lightbox, plain-text description, amenity badges, room cards, and reviews. No embedded map anywhere in the codebase — location is address text plus a "Get Directions" button that opens an external Google Maps link. Since zero hotels have coordinates (§06), this button has no real destination for any live listing today.

Highest-impact fix available — contact info hidden behind login

Call and WhatsApp CTAs only render as real tel:/wa.me links if the visitor is logged in; logged-out visitors get a "please log in" modal instead. WhatsApp has no visible affordance at all when logged out. Since 100% of live hotels are contact-only "imported" listings, this hides the site's only functioning conversion path from every first-time visitor — nearly everyone arriving from Google or social media.

Registration: single step — name, email, phone, password, plus Google OAuth. Low friction. Login has no "Forgot password" link anywhere — no self-service reset exists for travelers or owners at all (only admin/owner-triggered resets for cashier accounts).

Missing — no guest booking history

A logged-in traveler's "Dashboard" nav link resolves to the homepage. There is no /my-bookings route or component anywhere in the codebase. A guest who books a room has no way to review past or upcoming bookings after the confirmation screen.

Guest flow — friction points

  1. Homepage date picker is decorative — a functional bug, not a missing feature.
  2. Phone/WhatsApp contact hidden behind a login wall for anonymous visitors.
  3. No map on hotel detail pages, and no hotel has coordinates to show one anyway.
  4. No password reset for travelers/owners.
  5. No booking history / "my bookings" page.
  6. No amenities or room-type filter on search.
  7. No pagination — a larger inventory will load as one unpaginated list.
04

Hotel Owner Flow Analysis

Inferred from code

Bottleneck — no self-serve hotel creation

/register-hotel only creates the owner's personal account (name, email, phone, password) — zero hotel information is collected. Owners cannot create a listing under any circumstance; MyHotels has no "Add Hotel" button, and the underlying create form posts to an admin-only endpoint. The only paths to an owner having a hotel are an admin manually creating one or attaching the owner to an existing (often bulk-imported) record. Every owner signup today dead-ends on manual admin action.

Once attached, owners can edit address, phone, WhatsApp, website, Google Maps URL, description, and a fixed amenity checklist. Name and city are admin-only (owners must email support to change them). Photo upload is a real, complete feature: direct unsigned Cloudinary upload with progress bar, reorder, primary-photo selection, and a lightbox. Room types and pricing are fully editable.

Missing — availability calendar

No calendar UI exists anywhere. Inventory is two static integers (total_rooms / available_rooms) — an owner cannot block a specific date for maintenance or an event, only manually edit a count that conflates "temporarily unavailable" with "permanently reduced."

Analytics are genuinely strong: Recharts revenue area/pie charts, per-hotel bar chart, period-selectable revenue view, cashier performance stats. There is no listing-level views/clicks analytics, however — an owner can't tell if their listing is even being seen, only whether it converts.

Admin Panel Analysis

Inferred from code

Sections: Dashboard, Hotels, Owners, Cashiers, Import Hotels, Users. Hotel management is full CRUD (verify/suspend/edit/delete/attach-owner) plus a dedicated photo screen. Bulk Excel import is a genuinely sophisticated feature — header auto-detection, per-row preview with status/photo-count badges, batch naming, and an audit-trail history.

Critical — admin dashboard currently fails to build

frontend/src/pages/AdminDashboard.js (locally modified, uncommitted) contains a duplicate, orphaned "Performance Modal" JSX block sitting outside any function, between AdminUsers and AdminImport. Confirmed via a JS parser: throws Unexpected token. The last committed HEAD version parses cleanly and has no Users tab at all — this reads as in-progress, unfinished work. The admin dashboard cannot be built or deployed until this duplicate block is removed.

Owner approval has a proper pending queue with Approve/Reject. User management can view/filter/search all users and create any role, but has no per-row edit/deactivate in the general table. There is no dedicated bookings list/search view anywhere in the admin panel — only aggregate stats and per-cashier activity logs.

Worth investigating: google_places_hotels_dodoma.xlsx exists in the repo root, yet zero Dodoma hotels are live — either an unexecuted import or a targeting mismatch.

Performance

Verified live via repeated curl timing tests

Most severe finding in this audit

API TTFB across 5 separate runs: 13.8s / 17.3s / 14.0s / 15.1s / 18.6s. Not a cold-start fluke — consistent across repeated, spaced-out requests. Given the homepage's featured hotels and the entire search page depend on this same endpoint, this latency affects almost every meaningful interaction on the site, and on Tanzanian 3G would very plausibly cause timeouts or abandonment before results ever appear.

Security

Verified via code review + live header checks — the most severe issues in this audit

Critical

Unrestricted role self-assignment on public registration. POST /api/auth/register accepts a client-supplied role field with no server-side allowlist; is_verified is set True for anything but "owner". A single unauthenticated request with {"role":"admin",...} creates a fully-verified admin account with a working token — no credentials, no chained exploit. Top priority fix in this entire audit.

Critical

Unauthenticated payment confirmation + booking PII exposure. POST /api/bookings/{id}/confirm-payment has no auth dependency and never calls a real payment gateway — it trusts the client's submitted reference string. GET /api/bookings/{id} is also fully public, returning guest name/phone/email/payment reference. Booking refs (HS-{year}-{4 digits}) are realistically enumerable.

High

Broken authorization (IDOR) on hotel/room editing. Several endpoints check "deny only if role is owner AND not this hotel's owner" — traveler and cashier fall through with zero restriction. Affected: PUT/PATCH /api/hotels/{id}, POST /api/rooms, PUT/DELETE /api/rooms/{id}. Any self-registered traveler account can edit or delete another hotel's rooms today.

What's correctly configured

HTTPS is enforced with a proper redirect; security headers (X-Frame-Options, X-Content-Type-Options, X-XSS-Protection) are present. CORS uses an explicit origin allowlist, not a wildcard. Password hashing uses bcrypt correctly. No genuinely private key (payment secret, DB credential) was found exposed in frontend-served code — only expected-public identifiers (PostHog key, Google OAuth client ID, Cloudinary preset).

Competitive Gap Analysis

As a hotel directory (its current real-world state) vs. as a future booking platform

Missing for a hotel directory, today

  1. A visible phone number/WhatsApp without login — hiding the one thing a visitor needs undermines the actual product.
  2. A map/location view — zero coordinates exist and no map renders anywhere; table stakes for a physical-location product.
  3. Real descriptions and photos beyond Google-Places scrape defaults — near-zero description coverage makes listings feel identical and untrustworthy.

Missing for a future real booking platform

  1. A real payment gateway — an unauthenticated, gateway-free confirmation endpoint is not a viable foundation for real money.
  2. Availability calendar / date-blocking — without it, double-booking risk is real the moment more than one channel is used for the same room.
  3. Guest booking history — a booking product where a guest can't see their own bookings is missing a core category expectation.

What's Working Well

  • Cashier dashboard is genuinely well-designed and mobile-first — the clear template for bringing Owner/Admin up to the same bar.
  • Photo management (Cloudinary upload, reorder, primary selection, lightbox) is complete and polished on both owner and admin sides.
  • Revenue analytics (Recharts area/pie/bar, period selection, per-cashier performance) are more sophisticated than most early-stage hotel platforms bother building this early.
  • Bulk Excel import with per-row preview, validation, and audit-trail batches is a solid, well-thought-out admin tool.
  • Bilingual EN/SW support with a persistent language toggle shows real attention to the local market.
  • Guest checkout requires no forced account creation — good practice.
  • CORS is properly restrictive, and HTTPS is correctly enforced.
  • Homepage SEO fundamentals are genuinely good — the gap is everywhere else, not here.
  • Public-facing responsive design works well down to 375px.
